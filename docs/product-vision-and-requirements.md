# 海外主板维修能力建设：产品愿景与需求说明

## 1. 背景

海外售后在处理主板故障时，当前仍存在较多依赖专家经验和整板更换的情况。部分复杂主板维修依赖中方技术员专家现场处理，但这种方式成本较高、产能有限，且经验难以稳定复制给海外本地维修员。

本项目希望把制造中心、技术支持和海外现场积累的主板维修经验，逐步沉淀为可执行、可培训、可验证的数字化能力，降低不必要的整板更换，并建设可复制的海外主板维修能力。

## 2. 一句话目标

建设标准化主板故障诊断流程、维修知识库、2.5D 可视化操作工具和视觉 QC 数据链路，帮助海外售后减少不必要的整板更换，形成可复制的主板维修能力。

## 3. 终局愿景

长期目标是形成面向海外售后的主板故障检测与维修辅助系统；通用大模型聊天、问答和自主诊断不属于产品范围：

- 维修员能够按机型、故障现象和测试结果进入标准诊断路径；
- 系统能够展示关键测试点、常见故障模块、维修边界和修后验证要求；
- 视觉 CV 能基于经审核的 Golden Sample 和真实标签提出缺陷候选，并由人工确认或驳回；
- 后续可结合热成像、小型检测治具和专用视觉模型，逐步走向软硬件一体化的半自动检测。

## 4. 第一阶段范围

第一阶段不直接建设“AI 主板维修专家”，也不要求海外维修员立即掌握复杂主板维修。应先完成基础能力建设：

- 梳理高频、高成本主板故障；
- 建立诊断 SOP 模板；
- 建立主板维修知识库结构；
- 明确测试数据、图片、案例和修后验证记录的字段；
- 明确哪些故障可由海外本地处理，哪些必须升级给专家；
- 建立案例回流和知识更新机制。

## 5. 产品模块建议

### 5.1 诊断入口

维修员按机型、故障现象、维修阶段进入系统，例如不开机、不充电、无显示、无网络、摄像头异常、进水腐蚀等。

### 5.2 交互式 SOP

系统按步骤引导维修员完成检查：

- 当前步骤要测哪里；
- 需要使用什么工具；
- 正常范围或判断标准是什么；
- 异常时进入哪个分支；
- 是否需要拍照、记录电压/阻值/电流；
- 是否继续维修、升级专家或换板。

### 5.3 主板可视化资料

通过图片或交互式点位图展示：

- 测试点；
- 关键 IC；
- 常见故障区域；
- 连接器、充电通路、电源通路、射频、显示、音频等模块；
- 对应 SOP、维修视频或案例。

### 5.4 视觉 QC 辅助

视觉能力只输出受控候选，不直接作维修判定：

- 图片质量与配准状态检查；
- 与同板面 Golden Sample 的差异候选；
- 可见异常候选与器件位置关联；
- 人工确认、驳回和训练标签回写；
- 由结构化字段生成可追溯的 QC 与升级记录。

通用大模型聊天、知识问答、自由文本诊断和自主维修建议均已退役。历史 `/api/chat` 仅是关闭的遗留实现，不得恢复或扩展。

### 5.5 案例回流

每次维修应尽量沉淀为结构化案例：

- 机型；
- 故障现象；
- 测试数据；
- 图片或视频；
- 维修动作；
- 修后验证结果；
- 是否二返；
- 是否应更新 SOP 或知识库。

## 6. 当前仓库建议定位

当前仓库可作为“智能主板维修系统”的产品原型与后续工程主仓库。建议逐步从单文件原型演进为可维护系统：

- 保留现有原型能力；
- 逐步补充需求文档、资料边界、数据结构和开发任务；
- 后续再根据复杂度决定是否拆分前端、后端和知识库模块。

## 7. 当前有效部署与视觉架构

项目正式产品采用服务器主导的 Web 平台。全球维修员通过现有受控服务器上的统一入口使用维修工作台；海外维修员不上传视觉照片，也不进入内部视觉数据工作台。Milo 是实物照片的唯一来源，Codex 作为唯一数据操作员完成来源固化、验收合格交接、配准、标注、Golden Sample 管理和训练数据建设。

视觉处理采用异步混合架构：本地受控命令负责实物来源包、审计、质量/配准验收和 acceptance-qualified handoff；内部前端负责恢复已有服务器案例、状态展示、人工四点配准回退和候选确认；服务器负责案例身份、图片来源、任务状态、OpenCV 配准、Golden Sample 版本、差异候选、审核记录和数据导出。浏览器 IndexedDB 只保存本机编辑草稿，不是跨网点事实源，也不是实物上传入口。

上述 intake 与浏览器边界已于 2026-07-31 部署到生产 `08d08cd38aaffc9b01d901dfe9ef7684a614abac`。生产现已具备 qualified handoff、List V2、Detail V3、浏览器实物上传移除及受控 repair-evidence link 只读投影。实物数据仍只能经过来源审计、实物验收和验收合格交接进入，部署本身不构成现场精度、缺陷识别或维修效果证据。

首轮OpenCV在现有CPU服务器运行，负责图片质量、板框轮廓、ORB/AKAZE特征匹配、RANSAC单应性和差异候选。训练深度视觉模型使用独立算力环境，不在当前服务器完成。自动输出始终是候选，维修动作必须继续来自经过审核的点位图、原理图、维修手册和诊断SOP。

权威技术设计见 `docs/superpowers/specs/2026-07-20-visual-qc-server-architecture-design.md`。旧文档中“Windows维修工作站加本地Python服务”“浏览器本地存储为正式路径”或“离线推理为主要交付方式”的表述均已被该架构取代。
